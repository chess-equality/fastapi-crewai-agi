# FastAPI + CrewAI Integration Findings

This document summarizes the research for combining the
[FastAPI full-stack template](https://github.com/fastapi/full-stack-fastapi-template)
with the [CrewAI](https://crewai.com/open-source) agent framework, and it
proposes a concrete way to make the result repeatable as a project scaffold.

## 1. Goal Summary

1. Build new projects on **FastAPI** and the **CrewAI** agent framework.
2. Use the local full-stack FastAPI template at
   `~/localdev/source/python/full-stack-fastapi-template` as the base.
3. Add CrewAI and initialize it inside the project.
4. Package the outcome as a **repeatable template** for future projects.

## 2. FastAPI Full-Stack Template Overview

The template is a Docker-first, full-stack application generator that uses
[Copier](https://copier.readthedocs.io) to stamp out new projects.

### 2.1 Key Files and Layout

```text
full-stack-fastapi-template/
├── .python-version                # pins Python 3.14
├── pyproject.toml                 # uv workspace, members = ["backend"]
├── copier.yml                     # Copier questions (project_name, stack_name, ...)
├── .env                           # runtime configuration
├── compose.yml                    # Docker Compose stack (db, adminer, backend, prestart)
├── compose.override.yml           # local development overrides
├── backend/
│   ├── pyproject.toml             # FastAPI backend dependencies
│   ├── Dockerfile                 # python:3.14 + uv + built frontend
│   ├── app/
│   │   ├── main.py                # FastAPI app, entrypoint = app.main:app
│   │   ├── api/main.py            # root APIRouter, includes route modules
│   │   ├── api/routes/            # individual route modules (items, users, login, ...)
│   │   ├── core/config.py         # pydantic-settings based config
│   │   └── models.py              # SQLModel models
│   └── scripts/
│       ├── prestart.sh            # DB wait, alembic upgrade, initial data
│       └── test.sh                # pytest + coverage
└── frontend/
    ├── package.json               # React + Vite + shadcn/ui + Tailwind
    ├── src/                       # frontend source
    └── Dockerfile.playwright
```

### 2.2 Backend Dependencies

`../backend/pyproject.toml` uses:

- `fastapi[standard]>=0.141.1,<1.0.0`
- `pydantic>2.0`, `pydantic-settings>=2.2.1,<3.0.0`
- `sqlmodel>=0.0.39,<1.0.0`
- `uv` for dependency sync and a `python:3.14` Docker image
- `ruff` target `py314` and `mypy` strict

### 2.3 How the Template Is Reused Today

- Fork/clone and rename.
- Or use `copier copy https://github.com/fastapi/full-stack-fastapi-template <dest> --trust`.
- The `../copier.yml` file drives project personalization and a post-creation Python
  script updates `../.env.local`.

## 3. CrewAI Project Scaffolding Overview

CrewAI is installed as a Python package and provides a CLI (`crewai`) that
generates opinionated project structures.

### 3.1 Installation and CLI

```bash
# recommended by the docs
uv tool install crewai

# verify
crewai version
crewai create --help
```

Relevant commands:

```bash
crewai create crew <name>          # JSON-first (default)
crewai create crew <name> --classic # Python/YAML scaffold
crewai create flow <name>          # Flow with embedded crews
crewai create flow <name> --declarative
crewai install                     # install project dependencies
crewai run                         # run the crew or flow
```

### 3.2 Project Types

CrewAI projects are tagged in `../pyproject.toml`:

```toml
[tool.crewai]
type = "crew"   # or "flow"
```

- **Crew** (`type = "crew"`) — a single multi-agent crew.
- **Flow** (`type = "flow"`) — an orchestrated, event-driven workflow that can
  embed multiple crews, plain Python, and direct LLM calls.

### 3.3 JSON-First Crew Structure

Generated by `crewai create crew <name>`:

```text
my_crew/
├── .env
├── pyproject.toml        # [tool.crewai] type = "crew"
├── README.md
├── crew.jsonc            # crew, tasks, process, inputs
├── agents/
│   └── researcher.jsonc  # agent definitions
├── knowledge/
├── skills/
└── tools/
```

Running it:

```bash
crewai run
```

`crewai run` detects `crew.jsonc`, loads `agents/*.jsonc`, prompts for missing
inputs, and executes the crew.

For programmatic use inside a FastAPI app, a JSON-first crew can be loaded with
`crewai.project.load_crew`:

```python
from pathlib import Path
from crewai.project import load_crew

crew, default_inputs = load_crew(Path(__file__).parent / "crews" / "research_crew" / "crew.jsonc")
result = crew.kickoff(inputs={**default_inputs, "topic": "AI Agents"})
```

### 3.4 Classic Python/YAML Crew Structure

Generated by `crewai create crew <name> --classic`:

```text
my_crew/
├── pyproject.toml
├── src/my_crew/
│   ├── __init__.py
│   ├── crew.py              # @CrewBase class
│   ├── config/
│   │   ├── agents.yaml
│   │   └── tasks.yaml
│   └── tools/
│       └── custom_tool.py
```

A classic crew can be imported and run directly:

```python
from my_crew.crew import MyCrew

result = MyCrew().crew().kickoff(inputs={"topic": "AI Agents"})
```

### 3.5 Flow Structure

Generated by `crewai create flow <name>`:

```text
my_flow/
├── .env
├── pyproject.toml           # [tool.crewai] type = "flow"
├── README.md
└── src/my_flow/
    ├── __init__.py
    ├── main.py              # Flow class + kickoff() entry point
    ├── crews/
    │   └── poem_crew/
    │       ├── __init__.py
    │       ├── poem_crew.py # classic @CrewBase crew, or JSON loader
    │       └── config/
    │           ├── agents.yaml
    │           └── tasks.yaml
    └── tools/
        └── custom_tool.py
```

A flow can be imported and kicked off:

```python
from my_flow.main import MyFlow

result = MyFlow().kickoff(inputs={"topic": "AI Agents"})
```

Crews inside a flow are typically loaded with `load_crew` when they are JSON-first:

```python
from pathlib import Path
from crewai.project import load_crew


def kickoff_content_crew(inputs: dict):
    crew, default_inputs = load_crew(Path(__file__).with_name("crew.jsonc"))
    return crew.kickoff(inputs={**default_inputs, **inputs})
```

## 4. The Integration Dilemma

CrewAI's CLI creates a **standalone project** with its own `../pyproject.toml`,
`../uv.lock`, and `src/` package. The FastAPI full-stack template is also a
standalone, Docker-first project whose Python backend lives under `../backend`.
The dilemma is how to merge these two without ending up with two separate
runtimes or two `../pyproject.toml` files that cannot be installed together.

Three integration patterns are possible.

### 4.1 Option A — CrewAI as a Library Inside the FastAPI Backend (Recommended)

Add `crewai` and, if needed, `crewai-tools` as normal dependencies of the
FastAPI backend. Use the CLI only to **generate scaffolding once**, then move
or copy the generated code into `../backend/app/crews` so it becomes a regular
backend sub-package. Expose crews/flows through FastAPI API routes under
`app/api/routes/`.

**Why this is the best fit for the full-stack template:**

- Keeps one Docker image, one `uv` workspace, and one backend service.
- Uses the existing FastAPI route, settings, and auth patterns.
- Lets the frontend call `/api/v1/crews/{name}/kickoff` just like any other
  backend endpoint.
- Avoids duplicating `../pyproject.toml` or fighting `uv` workspace resolution.

**How it maps to the generated code:**

- For a **classic crew**: copy `src/my_crew/` into `backend/app/crews/my_crew/`
  and import from `app.crews.my_crew.crew`.
- For a **JSON-first crew**: copy `crew.jsonc` and `agents/*.jsonc` into
  `backend/app/crews/my_crew/` and use `load_crew()` to instantiate it.
- For a **flow**: copy `src/my_flow/` into `backend/app/crews/my_flow/` and
  import the `Flow` class from `main.py`.

Example route:

```python
# backend/app/api/routes/crews.py
from fastapi import APIRouter

from app.crews.my_flow.main import MyFlow

router = APIRouter()


@router.post("/crews/my-flow/kickoff")
def kickoff_my_flow(topic: str):
    result = MyFlow().kickoff(inputs={"topic": topic})
    return {"result": result}
```

Then include it in `../backend/app/api/main.py`:

```python
from app.api.routes import ..., crews

api_router.include_router(crews.router)
```

### 4.2 Option B — CrewAI as a Separate Service

Run `crewai create flow <name>` in a separate `crewai-service/` directory at the
project root, keep its own `../pyproject.toml` and `../uv.lock`, and add a tiny
FastAPI wrapper (or use CrewAI AMP) to expose a REST API. The main FastAPI
backend then calls this service over HTTP.

**Pros:**

- Strong isolation of CrewAI dependencies and runtime from the main backend.
- Easier to scale or deploy CrewAI workers independently.

**Cons:**

- Adds a second Docker service, networking, and a new health-check path.
- Requires a wrapper or AMP subscription; the generated scaffold does not ship
  with FastAPI.

### 4.3 Option C — CrewAI AMP (Managed Cloud)

Deploy crews to [CrewAI AMP](https://app.crewai.com). Each deployment receives a
unique URL (`https://your-crew-name.crewai.com`) and a Bearer token. The FastAPI
backend calls the AMP REST endpoints:

- `GET /inputs` — discover required inputs
- `POST /kickoff` — start a run
- `GET /status/{kickoff_id}` — poll for status

**Pros:**

- No CrewAI dependency in the backend image at all.
- Managed scaling and deployment.

**Cons:**

- Requires a CrewAI AMP account and API token.
- Less suitable if the goal is a fully self-hosted, repeatable template.

## 5. Critical Compatibility Issue: Python 3.14

The FastAPI full-stack template currently pins **Python 3.14**:

- `.python-version` = `3.14`
- `../backend/pyproject.toml` = `requires-python = ">=3.14,<4.0"`
- `../backend/Dockerfile` = `FROM python:3.14`
- `../backend/pyproject.toml` = `target-version = "py314"` for ruff

CrewAI requires **Python >=3.10 and <3.14**:

> "CrewAI requires `Python >=3.10 and <3.14`."

This is a hard conflict. The template cannot add `crewai` to `../backend/pyproject.toml`
without first lowering the Python requirement.

### 5.1 Recommended Fix

Downgrade the FastAPI backend to **Python 3.12 or 3.13**, both of which are
supported by FastAPI, Pydantic, SQLModel, and CrewAI. The files that must change
are:

- `.python-version`
- `../backend/pyproject.toml` `requires-python`
- `../backend/pyproject.toml` `tool.ruff.target-version`
- `../backend/Dockerfile` base image (`FROM python:3.14` → `FROM python:3.12` or `python:3.13`)

After the change, run `uv sync` and rebuild the Docker image.

## 6. Proposed Implementation Plan

The following plan uses **Option A** (CrewAI as a library inside the FastAPI
backend) because it keeps the architecture aligned with the existing full-stack
template.

### 6.1 Prepare the FastAPI Base

1. Copy or generate a new project from the full-stack template.
2. Lower Python to `3.12` or `3.13` (see Section 5.1).
3. Confirm the backend starts with `docker compose watch` or
   `cd backend && fastapi dev app/main.py`.

### 6.2 Add CrewAI to the Backend

Add to `../backend/pyproject.toml` dependencies:

```toml
dependencies = [
    ...,
    "crewai>=0.140.0",
    "crewai-tools>=0.40.0",
]
```

> Exact versions should be chosen after testing; the values above are
> placeholders. Use `uv add crewai crewai-tools` inside `../backend` to update
> both `../pyproject.toml` and `../uv.lock`.

Add LLM API keys to `../.env.local` (e.g. `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, etc.)
and load them through `app/core/config.py` or a separate `../.env.local` file.

### 6.3 Generate the Initial CrewAI Scaffolding

Use the CLI in a temporary location, then merge the pieces that matter into the
backend:

```bash
# 1. install the CLI
uv tool install crewai

# 2. scaffold a flow (recommended for FastAPI because it has a clear kickoff())
cd /tmp
crewai create flow my_agent_flow
cd my_agent_flow
```

The generated `src/my_agent_flow/` contains:

- `main.py` with a `Flow` subclass and a module-level `kickoff()` helper.
- `crews/poem_crew/` as a starter classic crew.
- `tools/custom_tool.py`.

Copy the relevant contents into the backend:

```text
backend/app/
├── crews/
│   ├── __init__.py
│   └── my_agent_flow/
│       ├── __init__.py
│       ├── main.py
│       ├── crews/
│       │   └── content_crew/
│       │       ├── __init__.py
│       │       ├── content_crew.py
│       │       └── crew.jsonc
│       └── tools/
│           ├── __init__.py
│           └── custom_tool.py
```

The `main.py` can keep its module-level `kickoff()` helper, or you can expose
`MyAgentFlow().kickoff(inputs=...)` directly.

### 6.4 Expose FastAPI Endpoints

Create `../backend/app/api/routes/crews.py`:

```python
from fastapi import APIRouter

from app.crews.my_agent_flow.main import MyAgentFlow

router = APIRouter()


@router.post("/crews/my-agent-flow/kickoff")
def kickoff_my_agent_flow(topic: str):
    flow = MyAgentFlow()
    result = flow.kickoff(inputs={"topic": topic})
    return {"result": result}
```

Register it in `../backend/app/api/main.py`:

```python
from app.api.routes import ..., crews

api_router.include_router(crews.router)
```

For long-running crews, consider running `kickoff()` in a `BackgroundTask` or a
Celery/RQ worker so the HTTP request returns immediately with a job ID.

### 6.5 Adapt the Scaffolding for Reuse

Goal 4 is to make the combined setup repeatable. The cleanest way is to turn the
merged project into a **Copier template**.

Option 1 — Extend the existing `../copier.yml`:

1. Copy the full-stack template into a new repository.
2. Add CrewAI-specific files (`backend/app/crews/...`, `routes/crews.py`,
   updated `../pyproject.toml`, `../.env.local` LLM keys).
3. Add new Copier questions for LLM provider, model, and API key.
4. Add a `_tasks` entry that runs a script to initialize the first crew/flow
   after generation.

Option 2 — Provide a setup script:

Create `scripts/init-crewai.sh` in the repository that:

1. Runs `copier copy` from the FastAPI full-stack template.
2. Patches Python to 3.12/3.13.
3. Adds `crewai` and `crewai-tools` to `../backend/pyproject.toml`.
4. Runs `crewai create flow <project_name>`.
5. Moves the generated `src/<project_name>/` into `../backend/app/crews`.
6. Adds the `crews.py` route module.

Option 3 — Use a custom `crewai create template`:

CrewAI supports `crewai create template <name>` for remote project templates.
You could publish the merged project as a template and generate new projects
with:

```bash
crewai create template fastapi-crewai my-new-project
```

This is the most idiomatic CrewAI reuse path, but it requires the template to be
hosted in a Git repository.

## 7. Risks and Open Decisions

- **Python version conflict** (Section 5) must be resolved before any
  `uv sync` or Docker build can succeed.  
  **Status: Resolved.** The FastAPI backend was downgraded to Python 3.12 in
  `.python-version`, `../backend/pyproject.toml`, and `../backend/Dockerfile`.
  `uv sync` and local Docker builds now work.
- **JSON-first vs classic crews**: JSON-first is the new default and works with
  `load_crew()`, but classic crews are easier to import as a Python class. For a
  FastAPI integration, classic or a flow with classic sub-crews may be the
  simplest first step.  
  **Status: Resolved for this scaffold.** A generated CrewAI Flow
  (`../backend/app/crews/demo_flow`) with a `kickoff(inputs: dict | None = None)`
  wrapper is used. JSON-first crews remain a future option via
  `crewai.project.load_crew`.
- **Synchronous `kickoff()`**: Crew/flow execution can take minutes. Running it
  inside a normal FastAPI endpoint will block the worker. Decide early whether
  to use `BackgroundTask`, a task queue, or an async wrapper.  
  **Status: Open / low-priority risk.** The `POST /api/v1/crews/{flow_name}/kickoff`
  endpoint is currently synchronous and will block the worker while the flow
  runs. This is acceptable for a demo/prototype. For production use, the route
  should be wrapped in `BackgroundTask`, a Celery/RQ job, or an async executor.
- **LLM provider configuration**: API keys must be injected via environment
  variables, not committed to the repository.  
  **Status: Resolved in code, open for user secret management.**
  `OPENAI_API_KEY`, `OPENAI_MODEL`, and `ANTHROPIC_API_KEY` are loaded from `../.env.local`
  via `../backend/app/core/config.py`. The keys are not committed. A real key must
  still be supplied by the user.
- **CrewAI AMP vs self-hosted**: If the team already uses AMP, Option C may be
  faster; otherwise Option A keeps the project fully open-source and local.  
  **Status: Resolved for self-hosted.** The current implementation is fully
  self-hosted inside FastAPI. CrewAI AMP remains a valid alternative if the team
  later wants a managed REST API.
- **Template maintenance**: Any future FastAPI template update must be merged
  manually unless the template is kept as a Copier fork with an upstream remote.  
  **Status: Resolved in part, ongoing.** A Git fork with an `upstream` remote
  and a branch-per-update workflow is documented in Section 10. Long-term
  automation via a Copier fork or a setup script remains a future option.

## 9. Repeatability / Using This as a Template

The generic `crews` router means you can add new CrewAI flows without touching FastAPI routing code. To use this project as a starting point for a new FastAPI + CrewAI project, the simplest path is a manual clone-and-customize:

```bash
git clone <this-repo> new-project
cd new-project
# 1. Update .env.local with your Postgres, secret, and LLM credentials.
# 2. (Optional) Replace or extend backend/app/crews/ with newly generated flows.
```

### Adding a new flow

1. Generate a new flow:

   ```bash
   uv run crewai create flow my_flow --skip_provider
   ```

2. Move the generated package into `../backend/app/crews`:

   ```bash
   cp -r my_flow/src/my_flow backend/app/crews/my_flow
   ```

3. Ensure `backend/app/crews/my_flow/main.py` exposes a top-level `kickoff(inputs: dict | None = None)` function.

4. Restart the backend. The router will automatically discover the new flow and expose:

   ```
   POST /api/v1/crews/my_flow/kickoff
   ```

### More automated options

For a more repeatable scaffold, the next step is to either:

1. **Publish this repository as a Copier template.** Extend the existing
   `../copier.yml` with questions for `OPENAI_API_KEY`, `OPENAI_MODEL`, etc., and
   keep the FastAPI template's `_tasks` post-generation script.
2. **Create a setup script.** A script in `scripts/init-crewai-flow.sh` can run
   `crewai create flow <name>`, move the generated `src/<name>/` package into
   `backend/app/crews/<name>`, and adapt `main.py` if needed.
3. **Publish as a CrewAI remote template.** CrewAI's CLI supports
   `crewai create template <url> <dest>`; hosting this repo as a template makes
   it reusable through the CrewAI CLI itself.

## 10. Upstream Update Workflow

This project is a fork of the FastAPI full-stack template. To keep it current with the least friction, use a short-lived integration branch for each upstream sync.

### Initial setup

```bash
git remote add upstream https://github.com/fastapi/full-stack-fastapi-template.git
git fetch upstream
```

If you prefer to use the local clone as the remote, replace the URL with the local path:
`/home/userone/localdev/source/python/full-stack-fastapi-template`.

### Branch-per-update workflow

1. Make sure `main` is clean.
2. Create a short-lived sync branch:

   ```bash
   git checkout -b sync-upstream-YYYY-MM-DD
   ```

3. Pull upstream changes:

   ```bash
   git fetch upstream
   git merge upstream/main
   ```

4. Resolve conflicts. The most likely conflict files are:

   - `../README.md` (we added a CrewAI quick start section)
   - `../backend/pyproject.toml` (Python version, dependencies, and ruff config)

5. Regenerate the lock file instead of trying to merge it manually. `../uv.lock` is ignored in `../.gitignore`:

   ```bash
   uv lock
   ```

6. Verify the merge:

   ```bash
   uv run ruff check .
   uv run pytest
   uv run fastapi dev app/main.py
   ```

7. Merge the sync branch into `main`:

   ```bash
   git checkout main
   git merge sync-upstream-YYYY-MM-DD
   ```

### Tips

- Enable `git rerere` to remember conflict resolutions:

  ```bash
  git config rerere.enabled true
  ```

- Tag releases after a successful sync, e.g.:

  ```bash
  git tag v2026.08.07
  ```

- Keep the divergence small: the current template adds 12 new files and modifies 10 existing files, with only 7 backend files touched. See sections 9 and 10 for details.
